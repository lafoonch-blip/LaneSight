### 2. The speed profile is physically impossible
Segment speeds from the stored `trajectory.lane`:

| Segment | Speed |
|---|---|
| 0–15 ft | ≈14.6 mph |
| 15–28 ft | ≈17.8 mph |
| 29–42 ft | ≈18.5 mph |
| 42–57 ft | ≈19.5 mph |

- A real ball loses about 1–3 mph down the lane. This one "gains" about 5 mph, which means the depth scale is compressed near the camera and stretched far away. That is the same calibration error that moves the boards.
- Far downlane the ball moves only about 1–2 px per frame in y. With this camera spot, a 1 px error is worth about a foot.

## Recommendation engine failures (`lanesight_core/insights/adjust.py`)
1. **No plausibility gate.** A shot with speed late > speed early (or a lateral jump of about 3 boards between neighboring samples, like the 4.76 spike at 42.5 ft) should downgrade far-lane metrics and return "Not enough reliable measurement", not a move.
2. **Unknown pins don't lower confidence.** With an unreadable deck it can't tell a strike from a miss, but it still recommends an 8-board move.
3. **Move size.** `n = min(4, round(boards/1.5))` allows feet 8 / target 4 in one shot. Typical coaching moves are 1–3 boards. Cap at 2-and-1 (or 3-and-1/2) unless several shots confirm the move.
4. **Breakpoint goes off the lane.** `project_breakpoint` extends a straight feet→arrows line to 42 ft and returns 0 (and −1 on earlier runs). Boards must clamp to 1–39. A straight-line projection is also wrong for a hooking ball.
5. **Intent mismatch.** The card shows Target 20 / 10 / 10, but `insights.execution = no_intent` and `classification = NO_INTENT`. `suggested_target` still used an intent. Upload intent isn't passed consistently into `strike_adjustment`, so the execution check (missed arrows by 1.7) never ran.
6. **Confidence and note hidden.** The rec is `confidence: low` with the note "Set your target line…", but the card shows a confident headline and an Apply button.
7. **Unit label.** The headline says "Move Right 8 **ft**". It should be boards.

## App/UI and data issues
- **Status mapping (iOS `Theme.swift` `MetricStatus`):** only `ok/measured/good` and `best_effort/watch/degraded` are handled. `low_confidence` and `calibrated_estimate` fall through to **UNAVAILABLE while still showing a value**. `Models.swift` has a separate mapping with `.estimate`, and the two disagree. Use one mapping, and show these as "Estimate".
- **Achievement progress formatting:** "16.635 / 20" and "359.359 / 450" need rounding. Rev Machine progress also uses an estimate-status rev rate.
- **Upload shows Score/achievement cards:** per DEC-055, uploads don't count toward these, so showing "Building your score 3/20" and "Close to unlocking" on an upload card is misleading.
- **Score data contaminated:** the 3 counted shots are this same clip uploaded into session `3338e9ec…` before DEC-055 (rows 03f7b6e8, bae3d3df, f2c0d0e5). Reset score/achievement data (allowed before Beta).
- **No duplicate guard:** the same file was stored 8 times. Hash the upload and warn or reuse.
- **Non-determinism:** 14b234c8 differs from the other runs of the same file (touchdown 4.202 vs 4.194, loft 1.16 vs 0.97, entry angle 3.45 vs 3.13, suggested feet 12 vs 15). The trim or re-encode is probably different. Analysis of the same frames should be repeatable.
